# R2 量測與記錄規則

[修改] 使用者要求：「裝載後當轉速不為 0 開始記錄，每半圈更新一次數值。但每半圈還是以整圈時間計算。比如正緣→正緣，負緣→負緣。所以一圈會有兩次數值。」

## 事件、計算與保存

GPIO3 設為 CHANGE。ISR 只記錄時間及電位，主迴圈按 RPM／LOAD 事件時間排序處理，沿用 LOAD 去抖。HIGH 事件使用上升沿時間基準，LOW 事件使用下降沿時間基準。

| 事件時間（us） | 邊沿 | 計算 | RPM | 曲線 raw |
|---:|---|---|---:|---:|
| 12000 | 上升 | 建立上升沿基準 | 尚無 | 不記錄 |
| 12250 | 下降 | 建立下降沿基準 | 尚無 | 不記錄 |
| 18000 | 上升 | 18000−12000＝6000 us／圈 | 10000 | 750 |
| 20250 | 下降 | 20250−12250＝8000 us／圈 | 7500 | 1000 |
| 24000 | 上升 | 24000−18000＝6000 us／圈 | 10000 | 750 |
| 28250 | 下降 | 28250−20250＝8000 us／圈 | 7500 | 1000 |

所得曲線是 `[750, 1000, 750, 1000, 0, …]`。即使這四筆全部發生在發射之前，發射與量測完成後仍會發布。第一圈尚在建立基準；穩定取得兩類邊沿後才是每圈兩筆。

[刪減] 不再以發射確認時間切掉前段資料，不再在發射時重置 Profile；沒有把 HIGH→LOW 或 LOW→HIGH 的時間乘二當整圈。

[保留] 前 32 筆固定保存，滿容量後繼續更新即時 RPM 與整次 MAX。發射後低於 MAX 的 20% 或無脈衝 300 ms 沿用既有結束流程；OLED 每 100 ms 刷新，BLE 整組結果於完成後發布。

## 重置與異常

| 情境 | 行為 |
|---|---|
| 未裝載 | RPM 事件不建立基準，不收曲線。 |
| 新一次裝載 | 清除兩類時間基準與本次曲線。 |
| 未發射且無事件 300 ms | 即時 RPM 歸零，清除兩類基準；重新旋轉後需各自再取得一個完整週期。既有本次曲線沿用。 |
| 裝載後停止 3 秒 | 沿用既有閒置重置，重新準備量測。 |
| 同類事件間隔過短／超過最高轉速 | 沿用既有有效值篩選，不移動該類有效時間基準。 |
| RPM／LOAD 佇列溢位 | 作廢該發 BBP 紀錄，清除兩類基準並重同步；重新裝載後恢復新 Shot。 |
| micros 回繞 | 使用 uint32 差值與既有事件排序。 |

註解：50 us 的異類脈寬不應套用整圈最小週期過濾；每類整圈 4000 us 仍為 15000 RPM。此項已由測試驗證。實板是否能捕捉更窄的脈波仍取決於感測器與中斷延遲。

## 與原 BBP 資料模型的關係

公開解析器 [atlas_bey 的 Profile 解析程式](https://github.com/shark-minister/atlas_bey/blob/main/core/src/result.cc) 將每筆 nRefs 解釋為一圈，使用 `dt = raw / 125` 換算毫秒並逐筆累加。[專案說明](https://github.com/shark-minister/atlas_bey) 也以拉轉起的各圈描述曲線。這支持「輸出的 Profile 以每圈一點解讀」，不能證明原廠內部韌體只使用單一邊沿。

[修改] R2 按本次要求每圈輸出兩個完整週期。單筆 raw 的單位及 RPM 換算保留，但相鄰數值來自重疊時間區間，原本每圈一點的時間累加方式不再等同實際經過時間。穩速 6000 us／圈時，每筆都是 raw 750；每圈兩筆，舊算法會累加成 12 ms。

註解：半圈更新表示每圈兩個感測事件。若感測標記不是半圈寬，兩事件可離得很近；不應假設固定 50% 佔空比。僅有 full-period raw 無法唯一重建每個交替邊沿的真實時間。若上位機之後需要精確時間軸，應另行設計能承載逐點時間的資料格式；本次不新增未約定欄位，也不自行丟掉一半讀值。
